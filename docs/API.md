# API Reference & Conventions

The **OpenAPI 3 schema** generated by drf-spectacular is the authoritative contract for REST:

- Schema: `GET /api/schema/` (YAML/JSON)
- Swagger UI: `/api/docs/` (development, and staff only in production)

This document covers the conventions behind that schema, the endpoint map, and the **WebSocket protocol**, which OpenAPI does not describe.

---

## 1. REST conventions

### Base URL & versioning

- All endpoints live under `/api/v1/`. A breaking change means `/api/v2/`. Additive changes stay in v1.
- JSON only (`Content-Type: application/json`). File bytes never go through the API (see Media).

### Authentication

- Cookie-based JWT (`access`, `refresh`). Clients never handle tokens directly.
- Unsafe methods (`POST`, `PUT`, `PATCH`, `DELETE`) must send the `X-CSRFToken` header, matching the `csrftoken` cookie.
- `401` with `code: "token_not_valid"` means the client should call `POST /auth/refresh` once, then retry.

### Resource naming

- Plural nouns, nested at most one level: `/servers/{id}/channels`, `/channels/{id}/messages`.
- IDs are UUID strings.
- Actions that aren't CRUD use sub-resources: `POST /servers/{id}/members/{user_id}/kick`.

### Pagination

- **Cursor pagination** for messages (implemented in Phase 3), notifications and audit logs:
  - `GET /channels/{id}/messages?limit=50` → newest first
  - `?before=<message_id>` (older history) or `?after=<message_id>` (backfill after reconnect)
  - Messages respond with `{ "results": [...], "has_more": bool }`. Without a cursor or with `before`, results are newest first. With `after`, they are oldest first (backfill). The cursor is simply a message id (UUIDv7, time-ordered).
- **Page-number pagination** (`?page=&page_size=`, max 100) for small, stable lists (discovery, members).

### Filtering, search, ordering

- `django-filter` query params, for example `?topic=gaming&q=python`.
- Message search: `GET /servers/{id}/messages/search?q=...&author=&channel=&has=attachment&before=&after=`.

### Errors

Every error has the same shape:

```json
{
  "type": "validation_error",          // validation_error | authentication_error | permission_denied | not_found | throttled | conflict | server_error
  "code": "invalid",                   // machine-readable
  "detail": "Human-readable summary.",
  "fields": { "email": ["Enter a valid email address."] },   // only for validation_error
  "request_id": "01J…"
}
```

| Status | Meaning |
|---|---|
| 400 | Validation error |
| 401 | Not authenticated / token expired |
| 403 | Authenticated but lacks permission (for a resource the user can see) |
| 404 | Not found, **or not visible to the user** (avoids leaking existence) |
| 409 | Conflict (duplicate nonce, already a member, …) |
| 429 | Throttled (`Retry-After` header included) |

### Idempotency

`POST /…/messages` accepts a client-generated `nonce`. A repeat of the same `(author, nonce)` returns the original message with `200` instead of creating a duplicate.

### Rate limits (initial values)

| Scope | Limit |
|---|---|
| `auth_login` | 5/min per IP + 10/hour per email |
| `auth_register`, `password_reset` | 5/hour per IP |
| `message_send` | 10 per 10 s per user (plus channel slow mode) |
| `media_sign` | 30/min per user |
| `invite_create` | 20/hour per user |
| `user` default | 120/min |
| `anon` default | 30/min |

### Messages — `/api/v1/` (same shape for channels and DMs)

| Method | Path | Description |
|---|---|---|
| GET | `/channels/{id}/messages` · `/dms/{id}/messages` | History (cursor) |
| POST | `/channels/{id}/messages` · `/dms/{id}/messages` ✱ | Send `{content, nonce, reply_to?, attachments?: [{public_id, filename}]}` (`poll` arrives in Phase 6). Content may be empty when there are attachments |
| PATCH | `/messages/{id}` | Edit own message (mentions follow the new text; no new notifications) |
| DELETE | `/messages/{id}` | Delete own message, or any with MANAGE_MESSAGES. Attachments are removed from Cloudinary |
| PUT/DELETE | `/messages/{id}/pin` | MANAGE_MESSAGES in channels; any participant in DMs. Max 50 per conversation |
| GET | `/channels/{id}/pins` · `/dms/{id}/pins` | Newest pin first |
| PUT/DELETE | `/messages/{id}/reactions/{emoji}` | Add/remove own reaction. Unicode emoji only; max 20 different per message; a new emoji needs ADD_REACTIONS |
| GET | `/messages/{id}/reactions/{emoji}` | Users who reacted (first 100) |
| POST | `/messages/{id}/report` | `{reason}` → report to site staff (Django admin). Not your own message; one open report per message and reporter |
| GET | `/servers/{id}/messages/search` · `/dms/{id}/messages/search` | Full-text search: `q` (web-search syntax: words, `"phrases"`, `-exclude`), `author`, `channel`, `has=attachment\|image\|file`, `before`/`after` (dates), `cursor`, `limit`. Returns `{results, total, next_cursor}`, newest first, only channels with READ_MESSAGE_HISTORY |

**Message payload** (REST and events): `id, channel_id | dm_id, author, type (default|reply|system), content, nonce, created_at, edited_at, pinned_at, reply_to {id, author, content, deleted, has_attachments} | null, attachments [{id, filename, content_type, size_bytes, width, height, is_image, url, preview_url}], reactions [{emoji, count, me}], mentions [user], mention_roles [{id, name, color}], mention_everyone`.

**Mentions** are stored as tokens: `<@user_id>`, `<@&role_id>` and `@everyone` (ADR-025). Clients render them with the `mentions`/`mention_roles` lists. `@everyone` needs MENTION_EVERYONE; a role mention notifies only if the role is mentionable or the author has MENTION_EVERYONE.

## 3. WebSocket protocol

### Endpoint & auth

- URL: `wss://<host>/ws/` (`ws://localhost/ws/` in development). `/ws/ping/` is an unauthenticated connectivity check.
- Auth: the access cookie is sent automatically with the handshake. `Origin` must match `ALLOWED_HOSTS`.
- One connection per browser tab. All subscriptions are multiplexed over it.

### Frame format

Every frame is a JSON object:

```json
{ "op": "event", "type": "message.created", "data": { … }, "seq": 1042 }
```

| Field | Description |
|---|---|
| `op` | `event` (server→client push), `request` (client→server), `response` (server reply to a request), `error` |
| `type` | Event or request name (`resource.verb`) |
| `id` | Client-chosen correlation ID on `request`, echoed on the `response` |
| `data` | Payload. Resource payloads use **the same serializers as REST** |
| `seq` | Per-connection increasing sequence number, used for debugging and gap detection |

### Subscriptions

Subscriptions are automatic (ADR-024). A connection receives events for the user (`user.{id}`), every server they belong to (`server.{id}`) and every channel they can view (`channel.{id}`). The server keeps these in sync when memberships, roles, overwrites or channels change. Clients never subscribe explicitly.

### Client → server requests

| type | data | Notes |
|---|---|---|
| `presence.heartbeat` | `{}` | Every `heartbeat_interval` ms (30 s). The response is `{}` |
| `presence.set` | `{status}` | `online` / `idle` / `dnd` / `invisible`. Saved to the profile. The response echoes the status |
| `typing.start` | `{channel_id}` or `{dm_id}` | Needs Send Messages (otherwise an `error` frame with `{code: "forbidden"}`). The server drops repeats within 2 s; clients send at most one every 5 s while typing |

A client may send up to 60 frames per 10 s. More closes the connection with `4429`. Unknown or malformed frames close it with `4400`.

> Messages are **not** sent over the WebSocket. They are sent with `POST /messages` (ADR-007).

### Server → client events

Structural events carry ids only. Clients refetch the resource over REST.

| type | Group | data |
|---|---|---|
| `ready` | — | `{user, session_id, heartbeat_interval, server_ids}`, sent right after connect |
| `message.created` | channel | Message + `server_id` (with `nonce` for the author's reconciliation) |
| `message.updated` | channel | Message + `server_id` |
| `message.deleted` | channel | `{id, channel_id, server_id}` |
| `typing.started` | channel | `{channel_id, user_id, username, display_name, expires_in: 8}` |
| `channel.created` / `channel.updated` / `channel.deleted` | server | `{server_id, id}` (`channel.updated` also covers overwrite changes) |
| `channel.reordered` | server | `{server_id}` |
| `category.created` / `category.updated` / `category.deleted` | server | `{server_id, id}` |
| `role.created` / `role.updated` / `role.deleted` | server | `{server_id, id}` |
| `role.reordered` | server | `{server_id}` |
| `server.updated` / `server.deleted` | server | `{server_id}` |
| `member.joined` / `member.updated` / `member.left` | server | `{server_id, user_id}` |
| `user.updated` | server | `{server_id, user_id}` (name or avatar changed) |
| `presence.updated` | server | `{user_id, status, version, server_id}`. `status` is `online`/`idle`/`dnd`/`offline` (invisible users appear offline). Ignore events with a lower `version` than the last one seen for that user |
| `read_state.updated` | user | `{channel_id \| dm_id, server_id, last_read_message_id, mention_count}` (syncs across tabs; for DMs the count is unread messages) |
| `reaction.added` / `reaction.removed` | channel / dm | `{message_id, emoji, user_id, count, channel_id, dm_id, server_id}` |
| `pins.updated` | channel / dm | `{channel_id, dm_id, server_id}`: refetch the pins list |
| `notification.created` / `notification.updated` | user | Notification (`updated`: a coalesced DM entry with a new count) |
| `notification.read` | user | `{ids}` (syncs other tabs) |
| `mute_settings.updated` | user | `{}` |
| `dm.created` / `dm.updated` | user | `{dm_id}`: refetch the conversation list |
| `dm.removed` | user | `{dm_id}`: you left or were removed |
| `server.joined` | user | `{server_id}`: you joined or created it; your connection is now subscribed |
| `server.access_changed` | user | `{server_id}`: your permissions or visible channels there changed |
| `server.removed` | user | `{server_id}`: you left, were removed, or the server was deleted |

Message events (`message.*`) are sent to `channel.{id}` or `dm.{id}` and carry `channel_id`, `dm_id` and `server_id`. `typing.started` carries `channel_id` or `dm_id`. `poll.updated` (channel / dm): `{message_id, poll (without my_votes), voter_id, voter_option_ids}` plus the scope; clients keep their own `my_votes` unless `voter_id` is them. `export.ready` / `export.failed` (user): `{export_id}`; a ready export also creates an `export_ready` notification.

### Close codes

| Code | Meaning | Client action |
|---|---|---|
| 1000 | Normal close | — |
| 1001 / 1006 | Server restart / network drop | Reconnect with backoff (1 s → 30 s max, with jitter), then backfill |
| 4400 | Malformed frame | Fix the client, don't retry the same frame |
| 4401 | Not authenticated, token expired, or session revoked (password change/reset, logout) | If the connection had reached `ready`, reconnect once with the current cookies. If refused before `ready`, `POST /auth/refresh` and reconnect. If the refresh fails, go to login |
| 4403 | Origin rejected / account disabled | Go to login |
| 4429 | Rate limited | Reconnect after the delay in the close reason |

### Groups (server-side)

| Group | Members |
|---|---|
| `user.{user_id}` | Every connection of that user |
| `server.{server_id}` | Connections of every member of that server |
| `channel.{channel_id}` | Connections of every member who can view that channel |
| `dm.{dm_id}` | Connections of every participant |

When permissions change (role edit, overwrite, removal), the consumers recompute their channel groups and send `server.access_changed` or `server.removed` to the affected users (ADR-024).
